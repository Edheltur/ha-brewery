# Pragmatic Domain-Driven Design

## 1. Цель и применимость

- Применяй DDD для управления сложностью предметной области, а не ради соответствия архитектурным шаблонам.
- Выбирай сложность модели пропорционально сложности правил, инвариантов и жизненных циклов, а не размеру кодовой базы или технической сложности системы.
- Для простых CRUD-операций, интеграций и вычислений предпочитай функции, простые структуры данных и Transaction Script.
- Не усложняй существующую архитектуру без конкретной задачи или выявленной проблемы.

## 2. Язык и границы предметной области

- Используй единый язык предметной области (Ubiquitous Language) в коде, тестах, требованиях и документации.
- Имена должны отражать назначение и смысл, а не используемый паттерн или технический механизм.
- Определяй границы моделей и ответственности (Bounded Contexts), если понятия, правила или причины изменений различаются.
- Не объединяй разные понятия в универсальную модель только из-за сходства их структуры. При необходимости явно преобразуй данные между контекстами.
- Не отождествляй контексты с микросервисами, репозиториями или отдельными базами данных.
- Сосредотачивай усилия на уникальной доменной логике; для типовых задач используй готовые решения.

## 3. Доменная логика и инварианты

- Сохраняй единый авторитетный источник реализации каждого доменного правила.
- Изолируй нетривиальные доменные правила от UI, транспорта, хранения и API фреймворков. Не допускай их дублирования в адаптерах.
- Отделяй валидацию внешнего ввода от проверки доменных инвариантов. Инварианты должны соблюдаться независимо от точки входа.
- Явно моделируй существенные состояния и допустимые переходы между ними. Не вводи конечный автомат, если достаточно простых условий.
- Предпочитай детерминированные функции и неизменяемые значения там, где это естественно. Классы с поведением используй, когда они помогают защищать состояние и инварианты.
- Не требуй объектно-ориентированной модели ради DDD. Функциональная модель и простые структуры данных допустимы.

## 4. Тактические паттерны

Применяй каждый паттерн только при наличии соответствующей задачи:

- **Entity** — когда важна идентичность объекта на протяжении его жизненного цикла.
- **Value Object** — когда значение имеет существенные ограничения, единицы измерения, семантику равенства или собственные операции. Не оборачивай каждый примитив.
- **Aggregate** — когда связанные изменения требуют общей границы согласованности. Определяй её по инвариантам, а не по графу объектов; выбирай минимальную достаточную границу. Защищай изменения через корень агрегата.
- **Domain Service** — когда доменная операция не принадлежит естественным образом одному объекту. Обычная функция допустима.
- **Repository** — когда необходима доменная абстракция загрузки и сохранения агрегатов. Не дублируй подходящие механизмы фреймворка.
- **Factory** — когда создание валидного объекта действительно сложно. В остальных случаях используй конструктор или функцию.
- **Domain Event** — когда факт предметной области имеет самостоятельное значение для других реакций. Не создавай события для каждого изменения поля и не вводи шину без необходимости.

## 5. Архитектура и инфраструктура

- Группируй код по смысловой связанности и причинам изменений, соблюдая необходимые соглашения фреймворка.
- Отделяй доменные решения от оркестрации и ввода-вывода. Не вводи обязательное количество архитектурных слоёв или каталогов.
- Изолированная доменная логика не должна зависеть от конкретной инфраструктуры. Интеграционный код может использовать API платформы напрямую.
- Используй абстракции, интерфейсы и DTO там, где они защищают реальную границу, устраняют существенную связанность или упрощают тестирование.
- Не навязывай Clean Architecture, Hexagonal Architecture, CQRS, Event Sourcing, микросервисы, Event Bus или DI-контейнеры как обязательные составляющие DDD.
- Выбирай модель согласованности по требованиям предметной области. Не заменяй простую корректную транзакцию распределённой или eventual consistency без обоснования.
- Не создавай расширяемость для гипотетических будущих требований (YAGNI).

## 6. Тестирование и ревью

- Проверяй нетривиальные доменные правила и инварианты без запуска инфраструктуры, где это практически возможно.
- Покрывай граничные значения, недопустимые состояния и переходы, отсутствие данных и конфликтующие входные условия, если они применимы.
- Проверяй наблюдаемое поведение, а не внутреннюю структуру классов. Интеграционными тестами проверяй реальные границы и взаимодействия.
- При ревью ищи не только недостаточную изоляцию логики, но и избыточные абстракции, дублирование правил, искусственные границы и ненужные слои.
- Обосновывай новые паттерны и существенные архитектурные изменения конкретной проблемой, преимуществом перед более простым решением и стоимостью сопровождения.
- Не превращай эти требования в формальный чек-лист обязательных артефактов: отдельные глоссарии, карты контекстов, диаграммы и ADR нужны только при практической пользе.

## Критерий принятия решения

Выбирай самое простое решение, которое корректно выражает предметную область, сохраняет необходимые инварианты и удовлетворяет актуальным требованиям. При равной корректности предпочитай меньшее число сущностей, зависимостей и уровней косвенности. Если паттерн увеличивает сложность без соразмерной пользы, не применяй его.
